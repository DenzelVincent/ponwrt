### 1.4 小结

GPON 的失败不是"注册被局端拒"，而是物理层 PMA 从未完成校准：`frequency_target` 停在 0x0013（u-boot 遗留窗口的原值），而 XG-PON 路径由驱动亲手写成 0xa49a；`frequency_level` 读到 0x0021。FL_OUT 的量级与线速无关（基础表 1G=0xa3d6、2500BASEX=0xa000、10GBASER=0x9edf），它表示"CDR 已被校准"，因此 0x21 等价于**根本没校准**，不是"信号弱导致锁不住"。

> **11-02 订正（本段只解释了"改前"）**：P1 把这条修实了——GPON 现在锁且落在窗内，`pon-fail` 为空。但业务仍然不通，因为断点挪到了更下面一层：**驱动在 GPON 制式下读写的是已经断电/无钟的 XGS MAC 块**（1.6）。所以本段里"0x21 等价于根本没校准"的推断方法本身仍然成立，被推翻的是它"唯一断点"的地位。另需注意：`frequency_level:0x0021` 这列 11-01 记自 SCSP 侧 PCS 寄存器（PCS 窗口一直是活的），不受 1.6 影响，仍是有效证据。

### 1.6 2026-11-02 真机定案：GPON MAC 是独立寄存器块，且我们的驱动没在用（P6 的来源）

设备树把 PON MAC 的**四个**窗口都交给了同一个平台设备（`1fb64000.ethernet`），驱动按 `reg-names` 取；"基址"不是一个，而是按制式分块。真机在 GPON 处于 hunt 循环时用 busybox `devmem` 直接读（`CONFIG_BUSYBOX_CONFIG_DEVMEM=y`，无需 `iomem=relaxed`，零重编）：

| reg-name | 基址/长度 | 驱动内的名字 | GPON 制式下实测 | 本轮采集覆盖 |
|---|---|---|---|---|
| `gpon` | 0x1fb64000 / 0x3e8 | `gpon_base`（**只**被 P3 的门控 dump 用到） | **活着**：逐偏移返回互不相同的真实值 | 已扫约 60 个偏移，未见一张偏移表能解释它们 |
| `xgpon` | 0x1fb65000 / 0xff8 | `xgpon_base`（GPON 路径 4 处 MAC 读写全在这里） | **黑的**：置 `GEPON_PHYSET10` bit31 后 `+0x00/+0x14/+0x318` 一律 `0xDEADBEEF` | 定点采过；bit31 之前同址读到 `sw_rst=0x00000000`、`ONU_ID=0x000003ff` |
| `epon` | 0x1fb66000 / 0x1000 | `epon_base` | 未采 | 拟作"该块是否被制式门控"的控制组 |
| `pon-phy` | 0x1faf0000 / 0x2000 | `pon_phy_base` | 正常，与 bundle 的 `phy_raw` 逐字节吻合 | 有效，1.3 表第 1-3 段的证据来源 |

`gpon` 窗样本（等级 A，原值）：`+0x000=0x000000FF`、`+0x040=0x80000000`、`+0x090=0xC`、`+0x0A0=0x18`、`+0x0E0=0x3A5D7BEC`、`+0x200=0x020000E9`、`+0x210=0xDEAD0400`、`+0x220=0x01520018`、`+0x260=0x20E`、`+0x370=0x88B60000`、`+0x3A0=0x10000001`。

三条由此得出的硬结论：

1. **`0xDEADBEEF` 是"字级 tie-off / 未上钟块"的固定返回值，不是总线错误**：`+0x210=0xDEAD0400` 这种"半 dead 半真值"只有同块内逐字门控才会出现；且 `deadbeef` 字面量在 feed 源码与 `patches-6.18/*.patch` 全量 grep 均不存在（等级 B），没有任何软件写过它。所以 `gpon` 窗内的非 dead 值都是真实读数，可以放心当证据用。
2. **驱动 GPON 路径全程在读写一个已断电/无钟的块**：`airoha-xpon-gpon.c` 的真实 MAC 访问只有 4 处（`:101` MBI_MPI_STOP、`:145` `readl_poll_timeout_atomic` on `AIROHA_XGPON_DBG_RESYNC`、`:182`/`:191` DBG_RESYNC 轮询与写），基址全是 `xgpon_base`；`gpon_base` 只出现在 `:927`-952 的诊断 dump。于是第 4-8 段的所有状态列（`dbg_rx_sync_st=0`、`int_status=0`、`phy_sta=0`、GTC 恒 `hunt`、`onu_id_raw`）**无法区分"没数据"和"看错了块"**。
3. **不能靠"基址平移"来修**：两块布局不同名。`gpon+0x00` 读到 `0xFF`（多位复位释放），而 `xgpon` 的 `SW_RST` 定义只有 `BIT(0)`；`+0x14` 在两块都读到 dead，无法证明它在 `gpon` 块里就是 ONU_ID。缺的是 **AN7581 GPON MAC 块的寄存器偏移表**，没有这张表，把 `xgpon_base` 换成 `gpon_base` 就是猜测性改动（本文不允许）。

**被本小节推翻的原判据**（回填时逐条订正，别再引用旧口径）：

| 原判据 | 推翻依据 |
|---|---|
| `GPON RX started ... ONU-ID=751 (valid)` → 说明 GPON 能读到合法 ONU-ID | `onu_id_raw=0xDEADBEEF`：`& GENMASK(9,0)` = `0x2EF` = 751，`BIT(15)` 恰为 1 → 幻值。P5 的验收判据在黑块上不成立 |
| `calibration_stage:11`(PLUG_OUT) 说明 P1 的记账没生效 | 它是每轮 `rx-stopped`→`stop_rx`→`plug_out` 的残留；`calibration_error:0` 时不表示失败。P1 的记账有效 |
| `gpon_window: skipped, mac not initialized` 只是 dump 没输出 | 是**门控条件选错**：`mac_initialized` 只在 `airoha-xpon-gpon.c:325`（`start_control` 路径，要求先 GTC 同步）置位，GPON 下恒 false → P3 新增的唯一证据通道在最需要它的模式下失效，见 P7 |

## 二、问题清单、改造方式与依据

### P1 GPON 分支完全跳过 PMA 校准（主因）

- 现象：39 次 rx_start 无一行 PrCal/EO/finished 日志，`freqdet_locked:0`（等级 A）
- 依据（等级 B）：
  - patch 608 `an7581_pcs_pon_start_rx()` 1959-1961 行：GPON 与 EPON_1G 一起被送到 legacy `an7581_pcs_bringup()`；`first_plug()` 在 1849-1851 行遇非 `10GBASER` 直接 `-EOPNOTSUPP`
  - patch 310-09 `an7581_pcs_phya_bringup()` 4562 行：`an7581_pcs_cdr_reset(..., calibrate = priv->manual_rx_calib)`；`manual_rx_calib` 只在 `airoha,an7581-pcs-eth` 且 product_id<0x2 时置位（310-09:1297-1305）→ **PON 口恒为 false**
  - 后果：`an7581_pcs_rx_prcal()` 不调用 → `SS_RX_FREQ_DET_1..4` 从不写、EO 扫描不做、`FORCE_RX_RDY` 不置
  - 交叉验证：`calibration_runs:0`、`calibration_stage:11`（=`AN7581_PON_STAGE_PLUG_OUT`，枚举见 608:918-931）对 GPON 是**预期值**，不能当 bug 报，只能作为"没走 first_plug"的旁证
- 改造方式（已按此实施，见第三节）：
  1. 不新写 GPON 专属 PMA 序列，改为把 legacy bringup 的校准门打开：新增 `an7581_pcs_pon_manual_calib()`（PON 口且 `pon_mode == GPON` 即为真），`an7581_pcs_phya_bringup()` 内两处 `priv->manual_rx_calib` 判断换成 `calibrate = priv->manual_rx_calib || an7581_pcs_pon_manual_calib(priv)`。生效范围已按代码确认：`calibrate` 传给 `an7581_pcs_cdr_reset()`，后者 `if (calibrate) an7581_pcs_rx_prcal()`（pcs-an7581.c:1799-1800），并且 `if (!calibrate) return 0` 之后的 FBCK_LOCK 重试循环（`goto retry_calibration`，上限 `AIROHA_PCS_MAX_CALIBRATION_TRY`）也随之路通。
  2. 该路径**不含** EO 扫描与 `FORCE_RX_RDY`（只在 `first_plug` 里做），因此 GPON 下 `eo_gain/eo_peaking/eo_fom` 与 `rx_ready_gate` 仍可能为 0，属于路径差异而非新缺陷；判读以 `PON low-rate bringup` 行的 `lock/fl/idac/window` 和 debugfs 的 `cdr_pr_idac`、`freqdet_locked` 为准。
  3. PrCal 目标值处理原则：**不猜**。GPON 的 `rx_interface` 在 `airoha_pcs_pon_config_rx()` 里就是 `PHY_INTERFACE_MODE_2500BASEX`，`an7581_pcs_rx_prcal()` 据此取 `target_fl_out = 0xa000`、`cyclecnt = 20000`、锁窗 `0xa000±100`（pcs-an7581.c:1636-1639、1656-1676），驱动不再写死第二个值；同时在 `an7581_pcs_pon_start_rx()` 的 GPON/EPON_1G 分支补一条 `PON low-rate bringup: mode= ret= lock= fl= idac= window=-` 实测打印（`dynamic debug` 对该路径无效，历史上已验证，故用 `dev_info`），由实测 `fl` 决定是否再引入 GPON 专属 target。retrain 走 `port->interface`（config 时已赋值为 2500BASEX，common.c:277/325），恢复阶梯的每次 retrain 也会带打印。
  4. 该分支同时补齐 `pon_stage`/`pon_calibration_runs`/`pon_last_error` 记账，使 debugfs 的 `calibration_stage` 不再恒为 11(PLUG_OUT)。
- 验收判据（已按实现改口径）：GPON 下 dmesg 出现 `PON low-rate bringup: mode=0 ... lock=1 fl=0x… idac=0x… window=0x…-0x…`；debugfs `freqdet_locked:1`、`cdr_pr_idac` 非 0、`frequency_target:0xa000`（该列取锁窗中点，`(0x9f9c+0xa064)/2`；打印格式为 `0x%04x`）。不再以 `PON PrCal` / `PMA sequence finished` 为准——那两行属于 `first_plug`，GPON 不走。
- 风险：若 2.488G 通道的实际 FL 量级与基础表不同，写死窗口仍不锁 → 此时依赖第 3 步打印的实测 fl 反推，不追加猜测性改动

### P2 AN7581 侧缺 GPON 模拟档表

- 依据（等级 B）：patch 608 的 AN7581 分支判断只覆盖 XGS 与 10G-EPON（992-1161 行的 `pon_mode` 条件里没有 GPON）；含 GPON 档 `{txpll=2, tx=5, rx=3, ana=2, preset=3}` 的是 AN7583 侧 `an7583_pcs_pon_rates[]`（2022-2035 行）
- 影响：即便补上 P1 的校准调用，preset/tx/ana/txpll 仍会落到 XGS 的档值（等级 C，取决于新代码怎么写）
- 改造方式（本轮未单独实施）：不新增 AN7581 档表。GPON 走 legacy bringup，模拟参数来自基础驱动按 `2500BASEX` 选出的档，外加 patch 608 对所有 PON 口统一施加的 `an7581_pcs_pon_apply_impedance_defaults()`（`an7581_xgpon_txpll/tx/rx/ana` 等表）。只有当 P1 生效后 `lock=0` 或 `fl` 明显偏离 0xa000，才把"独立 GPON 档表"提上日程——避免在没有实测反证时先改一组猜出来的模拟值。
- 验收判据（改口径）：不要求 `eo_fom` 非 0（EO 扫描只在 first_plug 路径）；改以 `PON low-rate bringup` 的 `lock`/`fl` 与 debugfs `cdr_pr_idac`、`xpon_setting0/1`、`wan_sel`、`xsi_sel` 判读模拟档是否合适。

### P3 第 5 段可能读错寄存器窗口（必须先排除的取证盲区）

- 依据：GPON 解调走 1.25G GEPON PHY 块（`airoha-xpon-gpon.c:80-81`：`PHYSET10 bit31` 选 GPON 帧格式；`:46` RX 模式用 `RX_SYNC_CTRL bit9`），但 `airoha_xpon_gpon_advance_gtc()`（714-766 行）读的是 XG-PON 的 `AIROHA_XGPON_PHY_DBG_RX_SYNC_ST`
- 风险等级：C（推断）。文件头注释声称"MAC/PHY 窗口 mode-multiplexed、4 态机取值一致"，但没有实测支撑
- 后果：若两个窗口不同，P1 修好后即使 GPON 真已同步，日志仍会显示 `hunt`，排查会被误导
- 改造方式（已实施，只加读数不改逻辑）：`airoha_xpon_gpon_debug_window()` 一次打印两组证据——① `phy_raw:` 行的 6 个原值（`RX_SYNC_CTRL 0x0a04`、`DBG_RX_SYNC_ST 0x0b1c`、`GEPON_PHYSET10 0x124`、PHY `INT_STATUS/INT_ENABLE`、`XG_PHY_STA`）；② 独立 `"gpon"` 窗口（0x1fb64000/0x3e8）按 8 word 一行全量 dump。窗口由 `airoha-xpon-main.c` 用 `platform_get_resource_byname(..., "gpon")` **可选**映射（缺失只影响 dump，不影响 probe），dump 以 `mac_initialized` 为前提门控（**该门控已于 11-02 判定为改坏，理由"避免读到无时钟块"被 1.6 证伪，恢复方式见 P7**）。`airoha-xpon-diagnostics.c` 的 `pcs` 节点在 GPON 分支调用它。
- 取证前提（等级 B）：本地全仓检索 `1fb64000` 只命中两个 DTSI，没有任何驱动或参考实现（含 `tmp/gpon-ref/` 里的 ufo1cn 补丁）读过该窗口，也没有 EN7581 GPON MAC 寄存器表——所以"GPON 状态在哪个窗口"只能由真机读数定性，代码里不做假设性改动。
- 验收判据：能明确回答"GPON 的 GTC 同步状态位到底在哪个窗口"；若 `gpon 0x…` 全为 0 或恒值而 `dbg_rx_sync_st` 随光纤通断变化，则当前"复用 XG-PON 窗口"成立
- **2026-11-02 定案（等级 A，但结论与原判据相反）**：窗口判据已经答出来了——**"复用 XG-PON 窗口"被证伪**，GPON MAC 是独立块 `0x1fb64000` 且活着，`xgpon` 块在 GPON 制式下整片返回 `0xDEADBEEF`（明细见 1.6）。但答案**不是靠 P3 的代码拿到的**：dump 被 `mac_initialized` 门控挡住（P7），是靠设备上零重编的 `devmem` 拿到的。P3 的映射改动本身保留有效（`gpon` 窗已在 DT 里、驱动已可选映射），要修的是它的门控条件。

### P4 debugfs 取证字段不足

- 依据（等级 B）：`airoha-xpon-diagnostics.c` 的 `pon_pcs_debug_show()` 原来打印的字段固定，不含 `idac`、`XPON_SETTING_0/1` 回读、`WAN_SEL`/`XSI` 回读；历史上已确认 idac/fl 只能从 dmesg 的 PrCal 行看
- 改造方式（已实施）：`airoha_pcs_pon_rx_status` 增 `cdr_pr_idac/xpon_setting0/xpon_setting1/wan_sel/xsi_sel` 5 个字段，`airoha_pcs_pon_get_rx_status()` 补齐这 5 次回读（PMA 两个 XPON_SETTING + `PXP_CDR_PR_IDAC`，SCU 的 `WAN_CONF`/`SSTR`），diagnostics 的 `pcs` 节点逐字段打印。`SS_RX_FREQ_DET_1..4` 的原值不进 debugfs 结构，改由 dmesg 的 `PON low-rate bringup` 行打印 `window=beg-end`（取自 `SS_RX_FREQ_DET_2`），一次 bundle 同时判读第 2、3、5 段
- 验收判据：GPON bundle 的 `debug-pcs.txt` 字段集与 XG-PON 完全对齐，可直接逐列比较

### P5 模式切换残留 ONU-ID

- 现象（等级 A）：kernel.log 336 行 `GPON RX started ... ONU-ID=751 (valid)`，而 `debug-registration.txt` 为 `onu_id:1023`
- 依据：`airoha-xpon-gpon.c:561` 只读 `AIROHA_XGPON_ONU_ID` 的 valid 位并打印；GPON ONU-ID 为 8bit（G.984.3），751 明显是上一次 XGS 注册的残留。代码里 `start_control`/`stop_rx`/`restart_mac` 都调 `airoha_xpon_clear_assignment()`，唯独 `prepare()`（由 `airoha-xpon-main.c:128` 分派）不清；真机在 GPON 下仍读到 751(valid)（等级 A），说明切换路径没有经过那三个清理点
- 改造方式（已实施）：`airoha_xpon_gpon_prepare()` 在释放 MAC 复位之后清 `ONU_ID_VALID | ONU_ID_MASK` → `0x3ff`，并同步 `xpon->onu_id`，其余清理路径不变（不在 prepare 里调用重量级的 `clear_assignment()`，避免在未建网口时动 OMCI/data-path）
- 验收判据：切到 GPON 首帧日志显示 `GPON RX started, ... ONU-ID=1023 (invalid)`
- **2026-11-02 订正（判据作废，改动保留）**：该判据在黑块上无法成立也无法证伪——`onu_id_raw=0xDEADBEEF` 经 `ONU_ID_MASK=GENMASK(9,0)` 解出 0x2EF=751、`BIT(15)` 恰为 1，所以 `751 (valid)` 是幻值而不是"残留"。改动本身（`prepare()` 清 `ONU_ID_VALID|MASK`→`0x3ff`）保留，因为它对 XGS→GPON 切换路径的清理语义无害且必要；但**验收要等 GPON 块偏移表到手后在正确的块上重测**。

### P6 GPON 路径读写的是错误 MAC 块，且缺 AN7581 GPON MAC 偏移表（当前主因）

- 现象（等级 A）：GPON 制式下 `xgpon` 块 0x1fb65000 整片读回 `0xDEADBEEF`，而 GPON 真正的块 0x1fb64000 有活值；驱动的 4 处 MAC 访问全在前者（`airoha-xpon-gpon.c:101`/`:145`/`:182`/`:191`）
- 依据：1.6 的四窗实测与三条硬结论；`deadbeef` 无软件写入来源（等级 B，全量 grep）
- 归属：第三方实现自带缺陷（1.7 的归因更正），不是本轮改动引入；作者标注"试验"，无真机注册成功的公开证据
- 影响：第 4-8 段全部读数不可解释；`recover-no-sync` 阶梯（24 轮）在对着黑块轮询，每轮的 `stop_rx`/`restart_mac` 都写进了没上钟的块——**这不是"注册失败"，是"根本没在跟硬件说话"**
- 改造方式（**本轮禁止实施**）：缺偏移表时把基址换成 `gpon_base` 属于猜测性改动，本文不允许（与 P1 的"target 不猜"同一原则）。前置条件是拿到两类证据之一：① 原厂 `econet,ecnt-xpon` 驱动里的 GPON 块偏移定义（阶段 S1，扫已到手的 `vendor.Image`）；② `gpon` 窗的"会动的寄存器"集合（阶段 S2，真机两次快照差分）。到手后的改造面按依赖顺序：
  1. 在 `airoha-xpon-gpon.h`/`private.h` 落一张 GPON 块偏移表（与 `xgpon` 表并列，**不做同名平移假设**）；
  2. GPON 路径 4 处 MAC 访问的基址从 `xgpon_base` 改 `gpon_base`，并逐个偏移替换；
  3. 中断处理：确认 GPON 用哪条中断线（`interrupts` 有 `mac`/`phy` 两条，见 P8）；
  4. 第 5 段的同步判据寄存器按 S2 结论替换（当前读的 `AIROHA_XGPON_DBG_RX_SYNC_ST` 属 `xgpon` 块）。
- 验收判据（分层，不接受"拨号成功"这种单点判据）：`gpon` 块里至少一个计数器类寄存器在 GPON 下有光时单调增长；`pon-trace-summary.txt` 的最大 seg 从 4 推进到 ≥5；`seg=5 gtc-sync-state` 出现非 `hunt` 值；随后第 6 段出现 `ploamd` 收包
- 代价与影响面：只动 feed 驱动 → 只重编 `airoha-xpon.ko`，不动 patch 608（不换内核 PREPARED stamp，不触发整棵内核重编）。但 `airoha-xpon-main.c` 是 XG-PON/XGS-PON 共享分发，改基址/中断必须回归 XGS 全流程（对照 1.1 的八段基线逐段比）
- 风险：若 S1/S2 都拿不到表，GPON 分支只能停在"结构就绪、寄存器未知"的状态；此时的止损是把 LuCI/ponctl 的 GPON 选项标为"取证专用，已知不通"，不再对外描述为可用（是否关闭 `mac_supported` 见第三节"错误改动评估与恢复"的第 3 项，本轮结论是**不关**，因为真机取证必须能切进 GPON 制式）

### P7 错误改动：P3 的窗口 dump 被 `mac_initialized` 自锁（本轮唯一确认写坏的东西）

- 依据（等级 B，代码可直接证明）：`airoha-xpon-gpon.c:935` 用 `if (!xpon->mac_initialized)` 直接打 `skipped` 返回；而 `mac_initialized = true` 在本文件只有 `:325` 一处，位于 `start_control` 之后的路径，**前提是 GTC 已同步**。GPON 下 GTC 永不同步（P6）→ dump 永不执行
- 后果：P3 新增的唯一证据通道在最需要它的模式下恒关，导致"P3 已实施"在真机上等于"什么都没测到"（bundle 里只有 `gpon_window: skipped`）。定案是靠设备 `devmem` 手工完成的，证据没有进 bundle、无法回归比对
- 恢复方式（三选一，建议第 1）：
  1. **去掉 `mac_initialized` 门控**，只保留 `gpon_base` 非空判断；诊断 dump 是纯只读，1.6 已证明读该块不挂总线（连无钟块都是固定返回值而非总线故障），这个门控当初防的风险不存在；同时把输出改成"按候选偏移列表 + 同一 bundle 内采两次"，让差分直接进 bundle
  2. 门控换成 `rx_active`（每轮 `rx_start` 后为真），保留"别在没开 RX 时读"的原意
  3. 不改驱动，把 dump 永久交给 `devmem` 脚本——代价是取证不可回归、判读全靠人肉贴日志
- 代价：`airoha-xpon-gpon.c` 一个函数（`airoha_xpon_gpon_debug_window()`），只重编 `.ko`；不碰 patch 608
- 验收判据：GPON bundle 的 `pcs` 节点出现逐行 `gpon 0x…` 原值而非 `skipped`；同一 bundle 内两个采样点对同一偏移可比
- 附带订正：该设计说明的原文在**第二节 P3 的"改造方式"**与**第三节 P3 行的结论列**（不在 1.5；1.5 只讲八段掩码），两处已就地标注"门控已判定为改坏"；其理由（怕读到无时钟块）已被 1.6 实测推翻——读无钟块得到的是固定 `0xDEADBEEF`，不是总线故障，所以门控防的风险并不存在，代价却是把唯一证据通道关掉

### P8 DT 与原厂不一致的两处（待查，不作为已定缺陷）

- 依据：1.6 的 DT 对照表（原厂 `vendor.dts.txt:314-332` vs `an7581.dtsi:452-466`），不一致本身等级 A，是否有害等级 C
- 两处：① `pon_phy` 的三个 reg（`1fa2ff24/4`、`1faf3000/fff`、`1faf4000/fff`）我们既没映射也没读过，其中 `1fa2ff24` 只有 4 字节、更像控制/状态寄存器；② `interrupt-names = "phy"` 那条我们写 `GIC_SPI 43`，原厂写 `SPI 34`
- 为什么不现在改：XG-PON 业务在现 DT 下完全正常（1.1 全八段），说明 `mac` 中断与已映射窗口够用；GPON 是否需要那两个未映射窗或依赖 phy 中断，只有 S1/S2 的结果能告诉我们要不要动
- 改造触发条件：S2 的差分指向 `1faf3000`/`1faf4000`，或确认 GPON 的收包/状态推进依赖 phy 中断且当前收不到 → 才按原厂补齐 reg 与中断号
- 代价：改 `an7581.dtsi` 属 `target/linux/airoha/dts`，不进 `$(PATCH_DIR)`，按 4.3.1 记的 stamp 判据理论上不触发整棵内核重编，只需重编 DTB 与重新打包 `sysupgrade.itb`（**这条判据本轮未在容器实测**，动 DT 前先在容器比对 `STAMP_PREPARED` 文件名变化再决定编译范围，别按理论走）

### 明确不在本文范围内（避免重复劳动）

- EN7572 前端 GPON 档位：`prepare()` 对 GPON/XGS 都用 A2 且无速率概念，只有 A2 表内 `TIA_BW/PGA_GAIN` 是否适合 2.488G 存疑。**作为 P1 完成后仍不锁时的下一分支**，现在不动。

### 4.3.3 GPON 窗差分取证（S2 用，零重编，设备 busybox 直接跑）

纯只读、不改任何寄存器；每条单行，差分用 `awk` 双文件（不依赖 busybox 里可能没有的 `paste`）。量级：`gpon` 窗 `0x3e8` 共 250 个 32bit 址，一轮快照秒级完成。

```sh
# ⓪ 先单点探一个址，确认读 gpon 块不挂总线（期望非 0xdeadbeef 的真实值；1.6 已证过一次，换固件后重跑一遍）
devmem 0x1fb64000 32

# ① 采之前确认制式与恢复轮数（无匹配就把整份 line 节点贴回来）
/usr/sbin/ponctl --device pon0 mode show; cat /sys/kernel/debug/airoha-xpon-pon0/line

# ② 第一次快照（十六进制址 + 值，两列便于 awk）
for a in $(seq $((0x1fb64000)) 4 $((0x1fb643e4))); do printf "%08x %08x\n" "$a" "$(devmem $a 32)"; done > /tmp/g1.txt

# ③ 等 20s（覆盖约 5 轮 3.6s 恢复阶梯）后第二次快照
sleep 20; for a in $(seq $((0x1fb64000)) 4 $((0x1fb643e4))); do printf "%08x %08x\n" "$a" "$(devmem $a 32)"; done > /tmp/g2.txt

# ④ 判据①/②：有址在涨＝数据进得来（判据寄存器读错了块）；零差异＝数据没进来（回 PMA/前端档位分支）
```
