# GPON 模式改造计划与排查台账

- 设备：Nokia XG-040G-MD（AN7581，光前端 EN7572，模块标识 GPON1968AN）
- 固件：分支 `AN7581-GPON`@d528c3b（改造前基线）。P1/P3/P4/P5 与其文档已推送：PonWrt `ea27fa074c`、drivers `4238f4b`、userspace `99ff123`。本轮全链路取证日志的三处改动**均已提交但尚未推送**：PonWrt `ac5653d2aa`（patch 608 的 seg2/seg3）、drivers `6e10673`（`airoha-xpon` 八段掩码）、userspace `89d29ca`（bundle 采集）；两个 feed 按分支固定（`feeds.conf.default:8-9` 的 `;gpon-mac` / `;gpon-luci`），必须先推送再 `feeds update`
- 证据来源：`pon-debug-2026-11-01T09-13-40-121Z`（bundle）、`kernel.log`、`system.log`（同一份日志内同时含 GPON 失败态与 XG-PON 健康态）
- 前提约束：同一光纤插普通 GPON 光猫可正常业务，**局端 GPON 下行（2.48832G@1490nm）确认存在**。因此本文只覆盖光猫侧驱动问题，不再讨论 OLT 制式、波长共存与账号绑定。
- 证据等级标记：`A`=设备实测日志/读数，`B`=代码可直接证明，`C`=推断（需实测才能定性）

### 1.2 无同步时的恢复阶梯（两种模式共用）

`airoha-xpon-xgpon.c:651-696` / `airoha-xpon-gpon.c:661`：每 `AIROHA_XPON_NO_SYNC_RECOVERY_MS`（实测 3.6s）触发一次 `stop_rx`→`start_rx`；每 5 次中 1 次做 full reinit（`pcs_profile_valid=false`，下一轮重跑完整 first_plug）。bundle 里 `rx_start_count:20`、`full_reinitializations:4`、`recoveries:18`，kernel.log 末尾已增长到 recovery 39。

### 1.4 小结

GPON 的失败不是"注册被局端拒"，而是物理层 PMA 从未完成校准：`frequency_target` 停在 0x0013（u-boot 遗留窗口的原值），而 XG-PON 路径由驱动亲手写成 0xa49a；`frequency_level` 读到 0x0021。FL_OUT 的量级与线速无关（基础表 1G=0xa3d6、2500BASEX=0xa000、10GBASER=0x9edf），它表示"CDR 已被校准"，因此 0x21 等价于**根本没校准**，不是"信号弱导致锁不住"。

### 1.5 全链路取证日志（八段掩码）

段号就是 1.1 表的第一列。驱动侧 `airoha-xpon` 与内核侧 PCS（patch 608）用同一套
`seg=`，一次 boot 的 dmesg 可以按段拼成完整时间线；`stage=` 是段内的具体落点。
行格式固定，便于 awk 直接聚合：

```
pon-trace: seg=<1-8> stage=<name> mode=<mode> k=v…        # mode：驱动侧为 gpon/xgpon/xgspon/epon-1g…，PCS 侧为 pon_mode 数字（GPON=0）
pon-fail:  seg=<1-8> stage=<name> mode=<mode> ret=<-errno> k=v…
```

| 段 | 宏名（驱动 / PCS） | 落点（`stage=`；★=不受掩码控制的 pon-fail） | 这一段能证伪什么 |
|---|---|---|---|
| 1 有光 | `…_SEG_RX` | `frontend-prepared`（前端档位 + `frontend_link` 的 PMA SETTING_0/1 与 SFP valid，非寄存器回读）、`optical-edge`（LOS 跃迁）、`recover-no-sync`；★`frontend-prepare`、★`recovery-start-rx` | 光在不在、恢复阶梯是不是在空转 |
| 2 PMA 校准 | `…_SEG_PMA` / `AIROHA_PCS_TRACE_SEG_PMA` | PCS：`legacy-start`、`phya-bringup`、`fbck-miss`、`fbck-locked`；★驱动 `pcs-retrain`、★PCS `config-bringup` | 校准到底有没有被调用、FBCK 有没有锁 |
| 3 制式落地 | `…_SEG_ANA` / `AIROHA_PCS_TRACE_SEG_ANA` | PCS：`line-configured`（WAN_SEL/XSI/interface 与 SETTING_0/1，均为**即将写入的值回显**）、`impedance-defaults`（ANA `RX_SIGDET_NOVTH` 与 PMA `TX_CALIB_0/1` 三个寄存器**读回**）；★`pcs-config`、★`mode-start` | 制式切换有没有执行、电气档落地后有没有被人改走 |
| 4 打开 MAC RX | `…_SEG_MAC` | `mac-prepared`、`gpon-framing`、`pcs-path`、`activate`、`rx-started`、`rx-stopped`、`mac-restart`；★`start-rx`、★`digital-rx` | RX 使能成不成功、走的 legacy 还是 first_plug |
| 5 帧同步 | `…_SEG_GTC` | `gtc-sync-state`（GPON，带 `physet10` 原值）/ `xgtc-sync-state`（XGS）；★`start-control` | P3 的窗口判读证据（同一同步态只打一次） |
| 6 PLOAM/注册 | `…_SEG_PLOAM` | `onu-state`（O1/O2_3/O4/O5/O7 名字，GPON 与 XGS 共用 `set_onu_state()`）、`assign-onu-id` | 局端有没有把 ONU 状态往上推 |
| 7 加密与上行 | `…_SEG_CTRL` | `ak-generated`、`arm-on`/`arm-off`、`arm-blocked`（阻塞条件位图）、`omci-link`；★`ak-generate`、★`arm-gate`、★`arm-upstream` | 上行不开究竟缺哪几项前置条件 |
| 8 T-CONT/GEM→业务 | `…_SEG_DATA` | `data-path-link`（netdev/ready/mapped/configured）；★`data-paths-entry`、★`data-paths-apply`、★`data-paths-count`、★`data-paths-conflict` | 业务映射与 carrier 何时起来 |

开关只有一个：`/sys/module/airoha_xpon/parameters/pon_trace`（`byte`，`0644`，默认
`0xff`）。bit0..bit7 对应第 1..8 段，`echo 0 >` 即退回只有摘要行的行为。PCS 是
built-in、没有自己的运行时参数，掩码由 `airoha_pcs_pon_set_trace()` 在每次
`activate_rx` 前下发（`airoha-xpon-main.c:167`，早于 `airoha_pcs_pon_config_rx()`
的首次调用），所以改完参数下一轮 `rx_start` 就生效，不必重载模块。

统一用 `dev_info`/`dev_warn` 而不是 `dev_dbg`：bringup 路径上 dynamic debug 实测
从不输出（历史轮次的逐步 `dev_dbg` 一次都没打出来），可见性只能由这个掩码控制。

防刷屏三条（已按此实现）：重试循环只打首次（`fbck-miss` 限 `calibration_try == 0`，
末次由既有 `dev_err` 与 `pon-fail` 覆盖）；轮询与 per-packet 路径只在状态跃迁时打
（`optical-edge` 比较前后光态、`gtc/xgtc-sync-state` 用 `trace_sync_seen` 位图按态去重、
`arm-blocked` 用 `trace_arm_block` 位图只在集合变化时打）；掩码为 0 时除 `pon-fail`
外不多打任何一行。

bundle 侧新增四个文件，由 `airoha-pon-debug` 的 `capture_trace_state()` 写出，写在
bundle 根目录（`collect` → `/tmp/airoha-pon-debug/bundle/`）和 `restart` 前快照目录
（`/tmp/airoha-pon-debug/pre-restart/`）各一份：`pon-trace-mask.txt`（掩码原值）、
`pon-trace.txt`、`pon-fail.txt`、`pon-trace-summary.txt`（按 `kind+seg+stage` 计数后
按段排序，用来一眼定位"断在第几段"）。放根目录而不是子目录：`dev_info()` 不带设备
前缀，dmesg 本身是全局的，本设备只有一个 PON MAC。

## 二、问题清单、改造方式与依据

### P1 GPON 分支完全跳过 PMA 校准（主因）

- 现象：39 次 rx_start 无一行 PrCal/EO/finished 日志，`freqdet_locked:0`（等级 A）
- 依据（等级 B）：
  - patch 608 `an7581_pcs_pon_start_rx()` 1959-1961 行：GPON 与 EPON_1G 一起被送到 legacy `an7581_pcs_bringup()`；`first_plug()` 在 1849-1851 行遇非 `10GBASER` 直接 `-EOPNOTSUPP`
  - patch 310-09 `an7581_pcs_phya_bringup()` 4562 行：`an7581_pcs_cdr_reset(..., calibrate = priv->manual_rx_calib)`；`manual_rx_calib` 只在 `airoha,an7581-pcs-eth` 且 product_id<0x2 时置位（310-09:1297-1305）→ **PON 口恒为 false**
  - 后果：`an7581_pcs_rx_prcal()` 不调用 → `SS_RX_FREQ_DET_1..4` 从不写、EO 扫描不做、`FORCE_RX_RDY` 不置
  - 交叉验证：`calibration_runs:0`、`calibration_stage:11`（=`AN7581_PON_STAGE_PLUG_OUT`，枚举见 608:918-931）对 GPON 是**预期值**，不能当 bug 报，只能作为"没走 first_plug"的旁证
- 改造方式（已按此实施，见第三节）：
  1. 不新写 GPON 专属 PMA 序列，改为把 legacy bringup 的校准门打开：新增 `an7581_pcs_pon_manual_calib()`（PON 口且 `pon_mode == GPON` 即为真），`an7581_pcs_phya_bringup()` 内两处 `priv->manual_rx_calib` 判断换成 `calibrate = priv->manual_rx_calib || an7581_pcs_pon_manual_calib(priv)`。生效范围已按代码确认：`calibrate` 传给 `an7581_pcs_cdr_reset()`，后者 `if (calibrate) an7581_pcs_rx_prcal()`（pcs-an7581.c:1799-1800），并且 `if (!calibrate) return 0` 之后的 FBCK_LOCK 重试循环（`goto retry_calibration`，上限 `AIROHA_PCS_MAX_CALIBRATION_TRY`）也随之路通。
  2. 该路径**不含** EO 扫描与 `FORCE_RX_RDY`（只在 `first_plug` 里做），因此 GPON 下 `eo_gain/eo_peaking/eo_fom` 与 `rx_ready_gate` 仍可能为 0，属于路径差异而非新缺陷；判读以 `PON low-rate bringup` 行的 `lock/fl/idac/window` 和 debugfs 的 `cdr_pr_idac`、`freqdet_locked` 为准。
  3. PrCal 目标值处理原则：**不猜**。GPON 的 `rx_interface` 在 `airoha_pcs_pon_config_rx()` 里就是 `PHY_INTERFACE_MODE_2500BASEX`，`an7581_pcs_rx_prcal()` 据此取 `target_fl_out = 0xa000`、`cyclecnt = 20000`、锁窗 `0xa000±100`（pcs-an7581.c:1636-1639、1656-1676），驱动不再写死第二个值；同时在 `an7581_pcs_pon_start_rx()` 的 GPON/EPON_1G 分支补一条 `PON low-rate bringup: mode= ret= lock= fl= idac= window=-` 实测打印（`dynamic debug` 对该路径无效，历史上已验证，故用 `dev_info`），由实测 `fl` 决定是否再引入 GPON 专属 target。retrain 走 `port->interface`（config 时已赋值为 2500BASEX，common.c:277/325），恢复阶梯的每次 retrain 也会带打印。
  4. 该分支同时补齐 `pon_stage`/`pon_calibration_runs`/`pon_last_error` 记账，使 debugfs 的 `calibration_stage` 不再恒为 11(PLUG_OUT)。
- 验收判据（已按实现改口径）：GPON 下 dmesg 出现 `PON low-rate bringup: mode=0 ... lock=1 fl=0x… idac=0x… window=0x…-0x…`；debugfs `freqdet_locked:1`、`cdr_pr_idac` 非 0、`frequency_target:0xa000`（该列取锁窗中点，`(0x9f9c+0xa064)/2`；打印格式为 `0x%04x`）。不再以 `PON PrCal` / `PMA sequence finished` 为准——那两行属于 `first_plug`，GPON 不走。
- 风险：若 2.488G 通道的实际 FL 量级与基础表不同，写死窗口仍不锁 → 此时依赖第 3 步打印的实测 fl 反推，不追加猜测性改动

### P2 AN7581 侧缺 GPON 模拟档表

- 依据（等级 B）：patch 608 的 AN7581 分支判断只覆盖 XGS 与 10G-EPON（992-1161 行的 `pon_mode` 条件里没有 GPON）；含 GPON 档 `{txpll=2, tx=5, rx=3, ana=2, preset=3}` 的是 AN7583 侧 `an7583_pcs_pon_rates[]`（2022-2035 行）
- 影响：即便补上 P1 的校准调用，preset/tx/ana/txpll 仍会落到 XGS 的档值（等级 C，取决于新代码怎么写）
- 改造方式（本轮未单独实施）：不新增 AN7581 档表。GPON 走 legacy bringup，模拟参数来自基础驱动按 `2500BASEX` 选出的档，外加 patch 608 对所有 PON 口统一施加的 `an7581_pcs_pon_apply_impedance_defaults()`（`an7581_xgpon_txpll/tx/rx/ana` 等表）。只有当 P1 生效后 `lock=0` 或 `fl` 明显偏离 0xa000，才把"独立 GPON 档表"提上日程——避免在没有实测反证时先改一组猜出来的模拟值。
- 验收判据（改口径）：不要求 `eo_fom` 非 0（EO 扫描只在 first_plug 路径）；改以 `PON low-rate bringup` 的 `lock`/`fl` 与 debugfs `cdr_pr_idac`、`xpon_setting0/1`、`wan_sel`、`xsi_sel` 判读模拟档是否合适。

### P3 第 5 段可能读错寄存器窗口（必须先排除的取证盲区）

- 依据：GPON 解调走 1.25G GEPON PHY 块（`airoha-xpon-gpon.c:80-81`：`PHYSET10 bit31` 选 GPON 帧格式；`:46` RX 模式用 `RX_SYNC_CTRL bit9`），但 `airoha_xpon_gpon_advance_gtc()`（714-766 行）读的是 XG-PON 的 `AIROHA_XGPON_PHY_DBG_RX_SYNC_ST`
- 风险等级：C（推断）。文件头注释声称"MAC/PHY 窗口 mode-multiplexed、4 态机取值一致"，但没有实测支撑
- 后果：若两个窗口不同，P1 修好后即使 GPON 真已同步，日志仍会显示 `hunt`，排查会被误导
- 改造方式（已实施，只加读数不改逻辑）：`airoha_xpon_gpon_debug_window()` 一次打印两组证据——① `phy_raw:` 行的 6 个原值（`RX_SYNC_CTRL 0x0a04`、`DBG_RX_SYNC_ST 0x0b1c`、`GEPON_PHYSET10 0x124`、PHY `INT_STATUS/INT_ENABLE`、`XG_PHY_STA`）；② 独立 `"gpon"` 窗口（0x1fb64000/0x3e8）按 8 word 一行全量 dump。窗口由 `airoha-xpon-main.c` 用 `platform_get_resource_byname(..., "gpon")` **可选**映射（缺失只影响 dump，不影响 probe），dump 以 `mac_initialized` 为前提门控。`airoha-xpon-diagnostics.c` 的 `pcs` 节点在 GPON 分支调用它。
- 取证前提（等级 B）：本地全仓检索 `1fb64000` 只命中两个 DTSI，没有任何驱动或参考实现（含 `tmp/gpon-ref/` 里的 ufo1cn 补丁）读过该窗口，也没有 EN7581 GPON MAC 寄存器表——所以"GPON 状态在哪个窗口"只能由真机读数定性，代码里不做假设性改动。
- 验收判据：能明确回答"GPON 的 GTC 同步状态位到底在哪个窗口"；若 `gpon 0x…` 全为 0 或恒值而 `dbg_rx_sync_st` 随光纤通断变化，则当前"复用 XG-PON 窗口"成立

### P4 debugfs 取证字段不足

- 依据（等级 B）：`airoha-xpon-diagnostics.c` 的 `pon_pcs_debug_show()` 原来打印的字段固定，不含 `idac`、`XPON_SETTING_0/1` 回读、`WAN_SEL`/`XSI` 回读；历史上已确认 idac/fl 只能从 dmesg 的 PrCal 行看

### P5 模式切换残留 ONU-ID

- 现象（等级 A）：kernel.log 336 行 `GPON RX started ... ONU-ID=751 (valid)`，而 `debug-registration.txt` 为 `onu_id:1023`
- 依据：`airoha-xpon-gpon.c:561` 只读 `AIROHA_XGPON_ONU_ID` 的 valid 位并打印；GPON ONU-ID 为 8bit（G.984.3），751 明显是上一次 XGS 注册的残留。代码里 `start_control`/`stop_rx`/`restart_mac` 都调 `airoha_xpon_clear_assignment()`，唯独 `prepare()`（由 `airoha-xpon-main.c:128` 分派）不清；真机在 GPON 下仍读到 751(valid)（等级 A），说明切换路径没有经过那三个清理点

- 验收判据：切到 GPON 首帧日志显示 `GPON RX started, ... ONU-ID=1023 (invalid)`

### 4.3.2 真机采集与判读（切到 gpon 后逐条执行）

```sh
/usr/sbin/ponctl --device pon0 mode show
cat /sys/module/airoha_xpon/parameters/pon_trace
dmesg | grep -E "pon-trace:|pon-fail:" | tail -60
dmesg | grep -E "PON low-rate bringup|No FBCK Lock|GPON RX started|PCS won" | tail -20
cat /sys/kernel/debug/airoha-xpon-pon0/pcs
/usr/sbin/airoha-pon-debug restart; sleep 20; /usr/sbin/airoha-pon-debug collect; ls -l /tmp/pon-debug.tar.gz
cat /tmp/airoha-pon-debug/bundle/pon-trace-summary.txt
```

判读顺序（先段后列）：`pon-trace-summary.txt` 先看"trace 行首次出现的最大 seg"与"每段有哪些 stage"，把断点收敛到一段；再回到该段的具体列（`pcs` 节点、`debug-pcs.txt`、dmesg 原行）取值。若 `pon_trace` 读到 0，说明掩码被关过，`pon-fail` 仍会在，但 `pon-trace` 只剩不到 8 行，此时先 `echo 0xff > /sys/module/airoha_xpon/parameters/pon_trace` 再等下一轮 rx_start。

| 读数 | 期望值 | 不满足时的分支 |
|---|---|---|
| `pon-trace-summary.txt` | 逐段连续：`seg=1 frontend-prepared`→`seg=2 legacy-start`→`seg=3 line-configured`→`seg=4 rx-started`→`seg=5 gtc-sync-state` | 缺 `seg=2 legacy-start` → `start_rx` 没进 PCS 分支，先查 `seg=4 activate`/`pcs-path` 的 `retrain`/`profile_valid`；有 `legacy-start` 无 `phya-bringup` → bringup 在前段就返回，取同轮的 `pon-fail seg=` |
| `seg=2` 的 `fbck-miss`/`fbck-locked` | 同一轮同一 `index` 至多 1 行 `fbck-miss`（门控 `calibration_try == 0`）+ 末尾一行 `fbck-locked try=N`；GPON 下 `N>0` 也算正常，只要最终 locked（重试次数上限 `AIROHA_PCS_MAX_CALIBRATION_TRY=50`） | 只有 `fbck-miss` 无 `fbck-locked`，且伴随 `pon-fail: seg=2 stage=config-bringup … ret=-5` → 校准调用了但不锁，进 P2/前端 A2 档位分支 |
| `seg=3` 的 `line-configured`/`impedance-defaults` | `line-configured` 的 `wan_sel=0`（GPON 分支应准备 `FIELD_PREP(AIROHA_SCU_WAN_SEL, 0)`）、`interface=` 是 `phy_interface_t` 的枚举序号（GPON 走 2500BASEX、XG-PON 走 10GBASER，两份 bundle 里必然不同；序号在容器 `grep -n 2500BASEX include/linux/phy_interface.h` 取，不在本文写死）、`setting0/1` 是刚写进 PMA 的前端电气档（**回显写入值**，不是读回）；`impedance-defaults` 为 `rx_sel=2 tx_term_p=1 tx_term_n=1`（写入默认档 `AN7581_PON_RX_IMPEDANCE_DEFAULT=0x2`、`…_TX_…=0x1`，这一行是**读回**） | `impedance-defaults` 与写入档不同**不是缺陷**，正是"读回而不回显常量"要抓的证据——说明 EFUSE=1 或后续表把它改过；`line-configured` 出现但 `impedance-defaults` 缺失 → 该次 bringup 没走 `port_type == AIROHA_PCS_PON` 分支，SCU 与 PCS 认到的口不一致 |
| `seg=7 arm-blocked` | 注册成功后消失并出现 `arm-on` | 长期 `blocked=0x…` 且集合不变 → 按 `airoha-xpon-ploam.c` 的 `AIROHA_XPON_ARM_*` 位定义逐项定位：bit0 stopping / bit1 无光 / bit2 MAC 未初始化 / bit3 默认 IK / bit4 AK / bit5 SN / bit6 burst profile / bit7 ONU 状态未到 O2_3-O5 / bit8 PMA 未 ready 或 RX 未同步 / bit9 TX 未同步 |
| `PON low-rate bringup` | `mode=0 ret=0 lock=1 fl≈0xa000 idac≠0x000 window=0x9f9c-0xa064` | `ret=-5`（`-EIO`）且出现 `No FBCK Lock … after 50 calibration try` → 按实测 `fl` 反推 target；`lock=0` 且 `fl` 远离 0xa000 → 启动 P2（AN7581 独立模拟档）并复查前端 A2 档位 |
| `pcs` 节点校准列 | `freqdet_locked:1`、`cdr_pr_idac` 非 0、`frequency_target:0xa000`、`calibration_stage:10`(RX_READY)、`calibration_runs`≥1 | `calibration_runs:0` → bringup 未被调用，先回到第 1 段查 `rx_start` 是否触发；`calibration_stage:12` → 取 `calibration_error` 原值 |
| `eo_gain/eo_peaking/eo_fom`、`rx_ready_gate` | 仍为 0 | 预期值，不是缺陷（EO 扫描与 `FORCE_RX_RDY` 只在 `first_plug` 路径） |
| `GPON RX started` | `ONU-ID=1023 (invalid)` | 仍读到 751(valid) → P5 未生效，确认切换走的是 `prepare()` |
| `phy_raw` / `gpon 0x…` | 至少一组随光纤通断变化 | 两组都恒 0 或恒值 → "复用 XG-PON 窗口"假设被证伪，先定窗口再谈第 5 段 |

### 4.4 回退方案

- P1/P2 只改 patch 608 的 GPON 分支与新增档表，XGS/10G-EPON 路径不受影响；若验证失败，可单文件回退到 d528c3b 的 608 patch，已跑通的 XG-PON/XGS-PON 业务不降级。
- T1 是纯取证层：真机若嫌 dmesg 噪声大（一次 boot 的量级按代码路径估算为 60~250 行，尚未经真机计数），`echo 0 > /sys/module/airoha_xpon/parameters/pon_trace` 即可静默，只有 `pon-fail` 继续打（它不受掩码控制，且只在失败分支出现）；不需要为此回退代码。`airoha_pcs_pon_set_trace()` 是新增导出符号，回退时必须连同 drivers 侧的调用点一起回退，否则 `airoha-xpon.ko` 会因未定义符号而加载失败。
