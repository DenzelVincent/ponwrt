### 1.4 小结

GPON 的失败不是"注册被局端拒"，而是物理层 PMA 从未完成校准：`frequency_target` 停在 0x0013（u-boot 遗留窗口的原值），而 XG-PON 路径由驱动亲手写成 0xa49a；`frequency_level` 读到 0x0021。FL_OUT 的量级与线速无关（基础表 1G=0xa3d6、2500BASEX=0xa000、10GBASER=0x9edf），它表示"CDR 已被校准"，因此 0x21 等价于**根本没校准**，不是"信号弱导致锁不住"。

> **11-02 订正（本段只解释了"改前"）**：P1 把这条修实了——GPON 现在锁且落在窗内，`pon-fail` 为空。但业务仍然不通，因为断点挪到了更下面一层：**驱动在 GPON 制式下读写的是已经断电/无钟的 XGS MAC 块**（1.6）。所以本段里"0x21 等价于根本没校准"的推断方法本身仍然成立，被推翻的是它"唯一断点"的地位。另需注意：`frequency_level:0x0021` 这列 11-01 记自 SCSP 侧 PCS 寄存器（PCS 窗口一直是活的），不受 1.6 影响，仍是有效证据。

### 1.6 2026-11-02 真机定案：GPON MAC 是独立寄存器块，且我们的驱动没在用（P6 的来源）

设备树把 PON MAC 的**四个**窗口都交给了同一个平台设备（`1fb64000.ethernet`），驱动按 `reg-names` 取；"基址"不是一个，而是按制式分块。真机在 GPON 处于 hunt 循环时用 busybox `devmem` 直接读（`CONFIG_BUSYBOX_CONFIG_DEVMEM=y`，无需 `iomem=relaxed`，零重编）：

| reg-name | 基址/长度 | 驱动内的名字 | GPON 制式下实测 | 本轮采集覆盖 |
|---|---|---|---|---|
| `gpon` | 0x1fb64000 / 0x3e8 | `gpon_base`（**只**被 P3 的门控 dump 用到） | **活着**：逐偏移返回互不相同的真实值 | 已扫约 60 个偏移，未见一张偏移表能解释它们 |
| `xgpon` | 0x1fb65000 / 0xff8 | `xgpon_base`（**11-02 代码复核：GPON 路径 50 处 MAC 访问全在这里**——4 处直接基址 + 46 处经内联访问器，另有共享层 ploam/xgpon/crypto 若干，见 P6） | **黑的**：置 `GEPON_PHYSET10` bit31 后 `+0x00/+0x14/+0x318` 一律 `0xDEADBEEF` | 定点采过；bit31 之前同址读到 `sw_rst=0x00000000`、`ONU_ID=0x000003ff` |
| `epon` | 0x1fb66000 / 0x1000 | `epon_base` | 未采 | 拟作"该块是否被制式门控"的控制组 |

`gpon` 窗样本（等级 A，原值）：`+0x000=0x000000FF`、`+0x040=0x80000000`、`+0x090=0xC`、`+0x0A0=0x18`、`+0x0E0=0x3A5D7BEC`、`+0x200=0x020000E9`、`+0x210=0xDEAD0400`、`+0x220=0x01520018`、`+0x260=0x20E`、`+0x370=0x88B60000`、`+0x3A0=0x10000001`。

## 二、问题清单、改造方式与依据

### P1 GPON 分支完全跳过 PMA 校准（主因）

- 现象：39 次 rx_start 无一行 PrCal/EO/finished 日志，`freqdet_locked:0`（等级 A）
- 依据（等级 B）：
  - patch 608 `an7581_pcs_pon_start_rx()` 1959-1961 行：GPON 与 EPON_1G 一起被送到 legacy `an7581_pcs_bringup()`；`first_plug()` 在 1849-1851 行遇非 `10GBASER` 直接 `-EOPNOTSUPP`
  - patch 310-09 `an7581_pcs_phya_bringup()` 4562 行：`an7581_pcs_cdr_reset(..., calibrate = priv->manual_rx_calib)`；`manual_rx_calib` 只在 `airoha,an7581-pcs-eth` 且 product_id<0x2 时置位（310-09:1297-1305）→ **PON 口恒为 false**
  - 后果：`an7581_pcs_rx_prcal()` 不调用 → `SS_RX_FREQ_DET_1..4` 从不写、EO 扫描不做、`FORCE_RX_RDY` 不置
  - 交叉验证：`calibration_runs:0`、`calibration_stage:11`（=`AN7581_PON_STAGE_PLUG_OUT`，枚举见 608:918-931）对 GPON 是**预期值**，不能当 bug 报，只能作为"没走 first_plug"的旁证
- 改造方式（已按此实施，见第三节）：
  1. 不新写 GPON 专属 PMA 序列，改为把 legacy bringup 的校准门打开：新增 `an7581_pcs_pon_manual_calib()`（PON 口且 `pon_mode == GPON` 即为真），`an7581_pcs_phya_bringup()` 内两处 `priv->manual_rx_calib` 判断换成 `calibrate = priv->manual_rx_calib || an7581_pcs_pon_manual_calib(priv)`。生效范围已按代码确认：`calibrate` 传给 `an7581_pcs_cdr_reset()`，后者 `if (calibrate) an7581_pcs_rx_prcal()`（pcs-an7581.c:1799-1800），并且 `if (!calibrate) return 0` 之后的 FBCK_LOCK 重试循环（`goto retry_calibration`，上限 `AIROHA_PCS_MAX_CALIBRATION_TRY`）也随之路通。
  2. 该路径**不含** EO 扫描与 `FORCE_RX_RDY`（只在 `first_plug` 里做），因此 GPON 下 `eo_gain/eo_peaking/eo_fom` 与 `rx_ready_gate` 仍可能为 0，属于路径差异而非新缺陷；判读以 `PON low-rate bringup` 行的 `lock/fl/idac/window` 和 debugfs 的 `cdr_pr_idac`、`freqdet_locked` 为准。
  3. PrCal 目标值处理原则：**不猜**。GPON 的 `rx_interface` 在 `airoha_pcs_pon_config_rx()` 里就是 `PHY_INTERFACE_MODE_2500BASEX`，`an7581_pcs_rx_prcal()` 据此取 `target_fl_out = 0xa000`、`cyclecnt = 20000`、锁窗 `0xa000±100`（pcs-an7581.c:1636-1639、1656-1676），驱动不再写死第二个值；同时在 `an7581_pcs_pon_start_rx()` 的 GPON/EPON_1G 分支补一条 `PON low-rate bringup: mode= ret= lock= fl= idac= window=-` 实测打印（`dynamic debug` 对该路径无效，历史上已验证，故用 `dev_info`），由实测 `fl` 决定是否再引入 GPON 专属 target。retrain 走 `port->interface`（config 时已赋值为 2500BASEX，common.c:277/325），恢复阶梯的每次 retrain 也会带打印。
  4. 该分支同时补齐 `pon_stage`/`pon_calibration_runs`/`pon_last_error` 记账，使 debugfs 的 `calibration_stage` 不再恒为 11(PLUG_OUT)。
- 验收判据（已按实现改口径）：GPON 下 dmesg 出现 `PON low-rate bringup: mode=0 ... lock=1 fl=0x… idac=0x… window=0x…-0x…`；debugfs `freqdet_locked:1`、`cdr_pr_idac` 非 0、`frequency_target:0xa000`（该列取锁窗中点，`(0x9f9c+0xa064)/2`；打印格式为 `0x%04x`）。不再以 `PON PrCal` / `PMA sequence finished` 为准——那两行属于 `first_plug`，GPON 不走。
- 风险：若 2.488G 通道的实际 FL 量级与基础表不同，写死窗口仍不锁 → 此时依赖第 3 步打印的实测 fl 反推，不追加猜测性改动

### P5 模式切换残留 ONU-ID

- 现象（等级 A）：kernel.log 336 行 `GPON RX started ... ONU-ID=751 (valid)`，而 `debug-registration.txt` 为 `onu_id:1023`
- 依据：`airoha-xpon-gpon.c:561` 只读 `AIROHA_XGPON_ONU_ID` 的 valid 位并打印；GPON ONU-ID 为 8bit（G.984.3），751 明显是上一次 XGS 注册的残留。代码里 `start_control`/`stop_rx`/`restart_mac` 都调 `airoha_xpon_clear_assignment()`，唯独 `prepare()`（由 `airoha-xpon-main.c:128` 分派）不清；真机在 GPON 下仍读到 751(valid)（等级 A），说明切换路径没有经过那三个清理点
- 改造方式（已实施）：`airoha_xpon_gpon_prepare()` 在释放 MAC 复位之后清 `ONU_ID_VALID | ONU_ID_MASK` → `0x3ff`，并同步 `xpon->onu_id`，其余清理路径不变（不在 prepare 里调用重量级的 `clear_assignment()`，避免在未建网口时动 OMCI/data-path）
- 验收判据（~~原判据~~，11-02 晚订正）：切到 GPON 首帧日志显示 `GPON RX started, ... ONU-ID=255 (invalid)`（GPON 为 8 bit ONU-ID、无效值 `0xFF`；`1023` 是 XGS 位域，已作废，见下条）
- **2026-11-02 订正（判据作废，改动保留）**：该判据在黑块上无法成立也无法证伪——`onu_id_raw=0xDEADBEEF` 经 `ONU_ID_MASK=GENMASK(9,0)` 解出 0x2EF=751、`BIT(15)` 恰为 1，所以 `751 (valid)` 是幻值而不是"残留"。改动本身（`prepare()` 清 `ONU_ID_VALID|MASK`→`0x3ff`）保留，因为它对 XGS→GPON 切换路径的清理语义无害且必要；但**验收要等基址换到 GPON 块后重测**（11-02 表已到手，1.9）。GPON 块的 ONU-ID 位域**与 XGS 不同构，不能照搬**：`gponDevDeactiveOnu`（`xpon.ko`，写 `0x4000`）逐指令读出的是 **`and w0,w0,#0xffff7fff`（清 bit15＝有效位）+ `strb #-1`（低字节＝`0xFF`）** ⇒ GPON 侧是 **8 bit ONT-ID（`bits[7:0]`，GPON TC 层规格如此）+ bit15 使能**，"无效/未注册"值是 **0xFF 且 bit15=0**，而不是 XGS 的 `0x3ff`+`BIT(15)`。1.6 实测 `gpon+0x000=0xFF` 正是这个"去激活"态。⇒ **S3-2a 的连带结论：现有 `ONU_ID_MASK=GENMASK(9,0)`/`ONU_ID_VALID=BIT(15)` 与"清成 1023"的写法在换块时必须同时改成 `GENMASK(7,0)`/清 0xFF，否则会把 8 bit 字段按 10 bit 写。**（等级 A，来源 `dis_xpon.txt` 的 `gponDevDeactiveOnu`；本条在 11-02 之前被误记为"与 XGS 同构"，已订正）。**11-02 晚已按此实施**（drivers `ff66f45`）：`AIROHA_GPON_ONU_ID_MASK=GENMASK(7,0)`、`AIROHA_GPON_ONU_ID_VALID=BIT(15)`、`AIROHA_GPON_ONU_ID_INVALID=0xff`，`prepare()` 与去激活路径都写 `0xff`；真机预期日志随之变为 `ONU-ID=255 (invalid)`

### P8 DT 与原厂不一致的两处（待查，不作为已定缺陷）

- 依据：1.6 的 DT 对照表（原厂 `vendor.dts.txt:314-332` vs `an7581.dtsi:452-466`），不一致本身等级 A，是否有害等级 C
- 两处：① `pon_phy` 的三个 reg（`1fa2ff24/4`、`1faf3000/fff`、`1faf4000/fff`）我们既没映射也没读过，其中 `1fa2ff24` 只有 4 字节、更像控制/状态寄存器；② `interrupt-names = "phy"` 那条我们写 `GIC_SPI 43`，原厂写 `SPI 34`
- **附带第三处（11-02 由 S4 的跨度互验发现，等级 A）**：我们的 `xgpon` 窗写 `0xff8`，而原厂 XGS 块被访问的偏移跨度是 `0xffc`（顶到块内 `0x5ff8`）⇒ **现映射比原厂少 4 字节**，`0x5ff8`（`DBG PROBE` 一类，见 `reg_table.txt` XGS 段）落在窗尾之外、`ioremap` 拿不到。XG-PON/XGS 业务不受影响（驱动从未读它），但取证时若按 1.9 的表去读 `0x1fb65ff8` 会得到映射外的地址。GPON 主线不受影响（GPON 跨度正好 `0x3e8` = 我们的窗长）。
- 为什么不现在改：XG-PON 业务在现 DT 下完全正常（1.1 全八段），说明 `mac` 中断与已映射窗口够用；GPON 是否需要那两个未映射窗或依赖 phy 中断，只有 S1/S2 的结果能告诉我们要不要动
- 改造触发条件：S2 的差分指向 `1faf3000`/`1faf4000`，或确认 GPON 的收包/状态推进依赖 phy 中断且当前收不到 → 才按原厂补齐 reg 与中断号
- 代价：改 `an7581.dtsi` 属 `target/linux/airoha/dts`，不进 `$(PATCH_DIR)`，按 4.3.1 记的 stamp 判据理论上不触发整棵内核重编，只需重编 DTB 与重新打包 `sysupgrade.itb`（**这条判据本轮未在容器实测**，动 DT 前先在容器比对 `STAMP_PREPARED` 文件名变化再决定编译范围，别按理论走）

### P9 GPON 路径复用 XGS 的 PLOAM 栈（11-02 代码复核新增，第 6 段的第二道阻塞）

- 依据（等级 A，代码可直接证明）：GPON 的 IRQ work 在 `airoha-xpon-gpon.c:455` 直接调用共享的 `airoha_xpon_drain_ploamd()`（ploam.c:1149 起），而这条栈从头到尾是 XGS 形状：
  1. **长度**：`drain_ploamd()` 用 `AIROHA_XGPON_PLOAMD_WORDS=13`（52 字节）判断 FIFO 是否够一包（ploam.c:1165），再按每字 4 字节大端拼包（:1169-1175）；GPON 下行 PLOAM 按 G.984.3 §8.1.3 是 **13 字节**（ONU-ID + Message ID + 10 字节净荷 + **CRC-8**）。gpon.c:60/63 已定义 `AIROHA_GPON_PLOAMD_BYTES`/`AIROHA_GPON_PLOAMU_BYTES`（13），但**全文件没有任何使用**。
  2. **校验**：`airoha_xpon_handle_ploamd()` 在 ploam.c:1096 用 `message[51] & BIT(0)` 当 **MIC 判决**，不过就 `-EBADMSG`；GPON 没有 MIC，也没有第 52 字节，13 字节包的最后一个字节是 CRC-8。⇒ 即便 drain 能拼出包，也会在入口被恒拒。
  3. **消息 ID**：共享 handler 的常量是 XGS 值（`AIROHA_XGPON_PLOAMD_*`：Assign_Alloc_ID=`0x0A`、Request_Registration=`0x09`、Deactivate=`0x05`），GPON 是 Assign_Alloc_ID=`0x09`、Request_Password=`0x07`、Deactivate_ONU_ID=`0x13`、Registration=`0x1E`（gpon.h:16-39 那套 `AIROHA_GPON_PLOAM_*` 枚举**定义了但零实现引用**）。同号不同义的两个最危险：`0x09` 在 GPON 是 Assign_Alloc_ID、在 XGS 是 Request_Registration；`0x05` 在 GPON 是 Password、在 XGS 是 Deactivate——直接复用会把下行密钥请求当成去激活、把 Alloc-ID 分配当成注册请求。
  4. **上行**：`send_ploamu()`（ploam.c:707 起）按 `AIROHA_XGPON_PLOAMU_WORDS=11`（44 字节）零填充写 FIFO；GPON 上行 PLOAM 是 13 字节/CRC-8，寄存器在 `0x4050 PLOAMu FIFO STATUS`/`0x4054 DATA`（1.9），激活消息序列是 Serial_Number_ONU(`0x02`)/Password(`0x05`)/Registration(`0x1E`)。现有 `airoha_xpon_send_registration()` 发的是 XGS 形状。
- 影响：**即使 P6 换块成功、第 5 段同步建立，第 6 段也不会推进**。`onu_state` 进入 O5、T-CONT/GEM 下发、AES 密钥交换都挂在这条栈上 ⇒ M5/M6 被 P9 二次阻塞。这是协议层格式问题，换基址/换偏移解决不了。
- 改造方式（并入 P6 的方案 B，不另立访问层）：
  1. 新增 GPON 专用 `airoha_xpon_gpon_drain_ploamd()` + `handle_ploamd()`：13 字节包、CRC-8 校验（多项式 `0x07`）、GPON 消息 ID 表；FIFO 用 `0x4058 STATUS`/`0x405C DATA`，状态字段的 used/overrun 位域**待 S4 第 3 步从 `gponDevGetPloamdFifoStatus` 一族抽取**，不按 XGS 的 `GENMASK(7,0)`/`BIT(31)` 照搬。
  2. 新增 GPON 专用上行发送（`0x4050/0x4054`，13 字节 + CRC-8），替换 `send_registration`/`send_ack` 在 GPON 路径的落点；消息顺序按 G.984.3 §9.2。
  3. `onu_state` 的 O1-O7 迁移与 GPON `0x40BC ONU STATE IN ACTIVATION` 的编码对齐（编码抽自 `gpon_act_change_gpon_state`）；AES 也不同于 XGS：GPON 块只有 `0x4060-0x4084` 的 superframe counter/active keys 0-3/shadow keys 0-3/软件切换，没有 `KEY_GEN`/`MSK`/`PIK` 的硬件派生（crypto.c 现全按 XGS 写）。
- 验收判据（改码后）：第 6 段出现 GPON 形状的 `PLOAMd: dest=… msg-id=0x… crc=valid` 日志（**不是** `mic=valid`），`stats.ploamd_accepted` 随 `0x4308` 增长而增长；seg=6 出数，`onu_state` 能进 O5。
- 为什么现在才列：原计划把第 6 段当作"换块后自然打通"；11-02 代码复核发现共享层根本没有 GPON 分支（P6 第 4 条），而 PLOAM 是其中协议格式差异最大的一段。单独立项是为了不让它被"换基址"掩盖，也便于在 S3 里单独排期与验收。

### P10 2a 之后第 5 段仍不通：判据错块 + 缺厂商 MAC 硬复位（11-02 刷机新增，当晚修复）

- 证据（bundle `pon-debug-2026-11-02T07-33-01-562Z`，全程 GPON、有光、`freqdet_locked:1`、`fl=0xa00b~0xa01d` 落窗）：`pcs` 节点的 34 行 dump **正常产出**（P7 验收通过），关键列为 `ONU_ID=0x000000ff`（P5 生效）、`INT_ENABLE=0`、`INT_STATUS=0x00000400`、`ACTIVATION_ST=0x00000001`（O1）、`MAC_SET=0x10000000`（**bit0=0**）、`RX_GTC_CNT=0`、`RX_GEM_CNT=0`、`RX_GEM_HDR_1BIT/2BIT/UC=0`、`PLOAMD_FIFO_STS=0`；PHY 侧 `dbg_rx_sync_st=0`、`phy_sta=0`、`physet10=0xff000000`（bit31=1）。trace 40 轮全部 `seg=5 … state=0 gtc_cnt=0x0 activation=0x1 mac_init=0`，`pon-fail` 为空
- **SSH 只读补采（11-02 晚，等级 A）**：对 `0x1fb643a0` 连采 60 点（约 20s、0.2s 间隔）发现 bit0 **并非恒定 0**——约每 21s 有 4s 读到 `0x10000001`，其余时间为 `0x10000000`；同时 `0x1fb64308/0x1fb64358/0x1fb640bc` 在所有采样里恒为 `0/0/1`。⇒ 复位/释放的混乱确实存在，但**"MAC 被按住"不足以解释计数器为 0**；即使 bit0=1 的 4s 窗口内也没有任何 GTC/超帧计数
- 代码根因（两条，等级 B）：
  1. `advance_gtc()` 用 **XGS PHY 的 `DBG_RX_SYNC_ST == SYNC_IN`** 作为进入 `start_control()` 的唯一门；该寄存器在 GPON 制式下恒 0（本 bundle 40 轮无一例外），所以 `start_control()` 永不执行。而 `MAC_SET` bit0 的"释放"只在 `start_control()` 里做，`prepare()/stop_rx()/restart_mac()` 又把它清 0——门控与释放互相等待，结构上与 P7 同类
  2. **2a 只做了 `MAC_SET` 的位操作，从未执行厂商给 PON MAC 的硬复位**。`gponDevResetCtrl` 反汇编（`dis_xpon.txt`）：复位时先 `gponDevMbiStop(1)/gponDevMpiStop(1)`，再对 **SCU `RSTCTRL1` 的 bit31 做“置位 1us → 清零”脉冲**，然后调 `gponDevSwReset`（`0x43A0` bit0 脉冲）；释放时 `MbiStop(0)/MpiStop(0)` 并写 `0x4228/0x422c = -1`。我们的驱动有 `xpon->scu` 却一次没用过这条复位线（`epon.c` 的 `epon_mac_reset()` 用的就是同一位），MAC 内部 GTC 接收逻辑可能根本没被初始化
- 因此**旧 bundle 的 `RX_GTC_CNT=0` 不能判为"没有下行数据"**：判据错块 + MAC 未经厂商复位，两个原因都会让计数器恒 0。原 4.3.2 的"delta=0 → 转 P2/前端"分支在修掉 P10 前**不成立**
- **修复（drivers `a7c98cf`，`ko` 级，未推送）**：新增 `airoha_xpon_gpon_hard_reset_mac()`＝SCU `RSTCTRL1[31]` 脉冲 + `MAC_SET` bit0 脉冲 + 释放 MBI/MPI + 清 `0x4228/0x422c`；`start_rx()` 在 PCS/数字 RX 就绪后调用它，随后 `INT_ENABLE=0`、清 `INT_STATUS`、记录 `RX_GTC_CNT/DS_SF_CNT` 初值；`prepare()/stop_rx()/restart_mac()` **不再把 bit0 留在 0**；`advance_gtc()` 的门控改为“`RX_GTC_CNT` 或 `DS_SF_CNT` 相对上一轮 250ms 轮询有增量”，`DBG_RX_SYNC_ST` 只随 trace 打印；新增 `gpon_gtc_last/gpon_sf_last` 两个字段与 `gtc-seen` trace 行
- **修复后的真机结果（11-02 晚，镜像含 `a7c98cf`，uptime≈1 min，等级 A）**：`strings airoha-xpon.ko` 见 `gtc-seen`/`GTC counters stalled` ⇒ 新代码在跑；`MAC_SET` 稳定为 `0x10000001`（复位释放已生效）；`PON low-rate bringup lock=1 fl=0x9ff4/0xa01f idac=0x455` 仍在窗内；但 30s 内 8+ 个恢复周期里 `RX_GTC_CNT`/`DS_SF_CNT`/GEM 头错误**全部为 0**，无 `gtc-seen`，`ACTIVATION_ST` 恒 1。⇒ 复位与判据修复是必要但不充分的
- **下一步的两个假设（待一次可逆试验区分）**：H1＝GPON 的 GTC 接收被激活态门控——厂商 `gpon_detect_phy_ready` 在 PHY ready 后先 `gpon_act_change_gpon_state(2)`（O2）再 `gpon_enable`，而我们每轮 `stop_rx` 写回 O1、`start_rx` 不写 O2，可能把接收关死；H2＝PHY/PCS 根本没把 GTC 帧送进 MAC（前端 A2 或 PCS 的 GPON 通路）。区分方法：在设备上把 `0x1fb640bc` 反复写成 2 并同时采 `0x1fb64308/0x358`（驱动 3.6s 会写回 O1，属可逆；BEN 未放行，无真实上行）——计数涨＝H1，仍 0＝H2
- 判读顺序：修后复测——**计数器涨 → 第 5 段真通**（`start_control()` 进入 O2_3）；**计数数器仍全 0 且已跨过 ≥4s 的 MAC 释放窗口 → 才轮到 P2/前端 A2 与 `bosa_en7572` 档位**，这才是有意义的负结果
- 附带记录（不另立项）：`cdr_pr_idac=0x458`（上一轮 0x3ff 满量程），**P1 的"idac 是否饱和"观察项关闭——不是持续饱和**；`eo_gain=1/eo_fom=449` 与 `calibration_stage=11` 是开机时 XGS `first_plug` 的结构体残留，GPON legacy 路径不写这些字段，不能当 GPON 读数
