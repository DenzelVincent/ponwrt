# GPON 模式改造计划与排查台账

- 设备：Nokia XG-040G-MD（AN7581，光前端 EN7572，模块标识 GPON1968AN）
- 固件：分支 `AN7581-GPON`@d528c3b，feeds `pon_drivers=6c021de`（gpon-mac）、`pon_userspace=99ff123`（gpon-luci）
- 证据来源：`pon-debug-2026-11-01T09-13-40-121Z`（bundle）、`kernel.log`、`system.log`（同一份日志内同时含 GPON 失败态与 XG-PON 健康态）
- 前提约束：同一光纤插普通 GPON 光猫可正常业务，**局端 GPON 下行（2.48832G@1490nm）确认存在**。因此本文只覆盖光猫侧驱动问题，不再讨论 OLT 制式、波长共存与账号绑定。
- 证据等级标记：`A`=设备实测日志/读数，`B`=代码可直接证明，`C`=推断（需实测才能定性）

### 1.2 无同步时的恢复阶梯（两种模式共用）

`airoha-xpon-xgpon.c:651-696` / `airoha-xpon-gpon.c:652`：每 `AIROHA_XPON_NO_SYNC_RECOVERY_MS`（实测 3.6s）触发一次 `stop_rx`→`start_rx`；每 5 次中 1 次做 full reinit（`pcs_profile_valid=false`，下一轮重跑完整 first_plug）。bundle 里 `rx_start_count:20`、`full_reinitializations:4`、`recoveries:18`，kernel.log 末尾已增长到 recovery 39。

### 1.3 GPON 逐段对齐

| 阶段 | GPON 应有的对应动作 | 实际读数 | 判定 |
|---|---|---|---|
| 1 有光 | 同基线 | `optical_signal:1`、`rx:-20.27dBm`、`los=0x00` | 通过 |
| 2 PMA 校准 | 应执行完整校准序列 | **39 次 rx_start，零行 `PON PrCal`、零行 `PMA sequence finished`**；`freqdet_locked:0`、`frequency_level:0x0021`、`frequency_target:0x0013`、`calibration_runs:0`、`eo_gain/peaking/fom:0`、`rx_ready_gate:0`、`phy_ready:0` | **唯一确证断点** |
| 3 制式落地 | `WAN_SEL=0`/`HSGMII`/`2500BASEX` | `PON line configured: mode=0, WAN_SEL=0` | 切换本身成功，但用的是"不校准"的 legacy bringup |
| 4 打开 MAC RX | `airoha-xpon-gpon.c:491-541` | `GPON RX started, irq=48, ONU-ID=751 (valid)` | 执行了；ONU-ID=751 为上次 XGS 注册残留（GPON ONU-ID 仅 8bit），见 P5 |
| 5 帧同步→O2_3 | `airoha-xpon-gpon.c:699-752` | `xgtc_sync:hunt`、`debug-mac available:0`、`xgtc_rx:0` | 未到达；第 2 段未锁时本段无意义，且存在 P3 盲区风险 |
| 6-8 注册/加密/业务 | PLOAMu SN、Assign-ONU-ID、EqD、GEM/T-CONT | `onu_state:O1`、`onu_id:1023`、`ploamd_rx:0`、`ploamu_tx:0`、`data_path_configured:0`、`service_ready:0` | 全部未执行，**当前不可判定** |

### 1.4 小结

GPON 的失败不是"注册被局端拒"，而是物理层 PMA 从未完成校准：`frequency_target` 停在 0x0013（u-boot 遗留窗口的原值），而 XG-PON 路径由驱动亲手写成 0xa49a；`frequency_level` 读到 0x0021。FL_OUT 的量级与线速无关（基础表 1G=0xa3d6、2500BASEX=0xa000、10GBASER=0x9edf），它表示"CDR 已被校准"，因此 0x21 等价于**根本没校准**，不是"信号弱导致锁不住"。

## 二、问题清单、改造方式与依据

### P1 GPON 分支完全跳过 PMA 校准（主因）

- 现象：39 次 rx_start 无一行 PrCal/EO/finished 日志，`freqdet_locked:0`（等级 A）
- 依据（等级 B）：
  - patch 608 `an7581_pcs_pon_start_rx()` 1959-1961 行：GPON 与 EPON_1G 一起被送到 legacy `an7581_pcs_bringup()`；`first_plug()` 在 1849-1851 行遇非 `10GBASER` 直接 `-EOPNOTSUPP`
  - patch 310-09 `an7581_pcs_phya_bringup()` 4562 行：`an7581_pcs_cdr_reset(..., calibrate = priv->manual_rx_calib)`；`manual_rx_calib` 只在 `airoha,an7581-pcs-eth` 且 product_id<0x2 时置位（310-09:1297-1305）→ **PON 口恒为 false**
  - 后果：`an7581_pcs_rx_prcal()` 不调用 → `SS_RX_FREQ_DET_1..4` 从不写、EO 扫描不做、`FORCE_RX_RDY` 不置
  - 交叉验证：`calibration_runs:0`、`calibration_stage:11`（=`AN7581_PON_STAGE_PLUG_OUT`，枚举见 608:918-931）对 GPON 是**预期值**，不能当 bug 报，只能作为"没走 first_plug"的旁证
- 改造方式：
  1. 为 GPON 建立独立的 PMA 序列入口（放开 `first_plug` 的 `10GBASER` 硬门，或新增 `an7581_pcs_pon_gpon_plug()`），按顺序执行 static→preset→TDC off→RX on→PrCal→L2R→各 cal→L2D→TDC on→RX_RDY→normal data
  2. PrCal 目标值处理原则：**不猜**。先按基础表 `2500BASEX = 0xa000±100` 写窗口，同时把实测 `fl`、`idac` 逐步打印；用实测决定是否需要 GPON 专属 target
  3. 每步加 `pr_info`（dynamic debug 对该路径无效，历史上已验证）
- 验收判据：GPON 下出现 `PON PrCal: mode=0 ... lock=1` 与 `PMA sequence finished: mode=0 lock=1 ...`；debugfs `freqdet_locked:1`、`phy_ready:1`
- 风险：若 2.488G 通道的实际 FL 量级与基础表不同，写死窗口仍不锁 → 此时依赖第 2 步打印的实测 fl 反推，不追加猜测性改动

### P2 AN7581 侧缺 GPON 模拟档表

- 依据（等级 B）：patch 608 的 AN7581 分支判断只覆盖 XGS 与 10G-EPON（992-1161 行的 `pon_mode` 条件里没有 GPON）；含 GPON 档 `{txpll=2, tx=5, rx=3, ana=2, preset=3}` 的是 AN7583 侧 `an7583_pcs_pon_rates[]`（2022-2035 行）
- 影响：即便补上 P1 的校准调用，preset/tx/ana/txpll 仍会落到 XGS 的档值（等级 C，取决于新代码怎么写）
- 改造方式：在 AN7581 侧新增按模式的档表（结构对齐 AN7583），GPON 档初值取 AN7583 表，并在 debugfs 打印"命中了哪一档"，由实测 EO/fom 与 lock 结果决定是否需要调整
- 验收判据：debugfs 能显示 GPON 档命中项；`eo_fom` 非 0

### P3 第 5 段可能读错寄存器窗口（必须先排除的取证盲区）

- 依据：GPON 解调走 1.25G GEPON PHY 块（`airoha-xpon-gpon.c:68-75`：`PHYSET10 bit31` 选 GPON 帧格式；`:40` RX 模式用 `RX_SYNC_CTRL bit9`），但 `airoha_xpon_gpon_advance_gtc()`（699-752 行）读的是 XG-PON 的 `AIROHA_XGPON_PHY_DBG_RX_SYNC_ST`
- 风险等级：C（推断）。文件头注释声称"MAC/PHY 窗口 mode-multiplexed、4 态机取值一致"，但没有实测支撑
- 后果：若两个窗口不同，P1 修好后即使 GPON 真已同步，日志仍会显示 `hunt`，排查会被误导
- 改造方式：把 sync 状态寄存器的**原始 32bit 值**和 GEPON PHY 块的对应状态寄存器一起打进 debugfs/dmesg，一次抓包定性；不改逻辑，只加读数
- 验收判据：能明确回答"GPON 的 GTC 同步状态位到底在哪个窗口"

### P4 debugfs 取证字段不足

- 依据（等级 B）：`airoha-xpon-diagnostics.c:431-444` 当前 `pcs` 节点字段固定，不含 `idac`、`SS_RX_FREQ_DET_1..4` 原值、`XPON_SETTING_0/1` 回读、`WAN_SEL`/`XSI` 回读、档表命中项；历史上已确认 idac/fl 只能从 dmesg 的 PrCal 行看
- 改造方式：在 `pcs` 节点补上述字段（patch 608 的 `airoha_pcs_pon_get_rx_status()` 200-276 行扩字段 + diagnostics 打印），使一次 bundle 能同时判读第 2、3、5 段
- 验收判据：GPON bundle 的 `debug-pcs.txt` 字段集与 XG-PON 完全对齐，可直接逐列比较

### P5 模式切换残留 ONU-ID

- 现象（等级 A）：kernel.log 336 行 `GPON RX started ... ONU-ID=751 (valid)`，而 `debug-registration.txt` 为 `onu_id:1023`
- 依据：`airoha-xpon-gpon.c:544` 附近只读 `AIROHA_XGPON_ONU_ID` 的 valid 位，切模式不清寄存器；GPON ONU-ID 为 8bit（G.984.3），751 明显是上一次 XGS 注册的残留
- 影响：对第 2 段的断点无因果关系，但会在 P1 修复后误导 O2/O3 判读
- 改造方式：`prepare`/`stop_rx` 时清 `ONU_ID_VALID`，日志措辞同步
- 验收判据：切到 GPON 首帧日志显示 `ONU-ID=... (invalid)`

### 明确不在本文范围内（避免重复劳动）

- EN7572 前端 GPON 档位：`prepare()` 对 GPON/XGS 都用 A2 且无速率概念，只有 A2 表内 `TIA_BW/PGA_GAIN` 是否适合 2.488G 存疑。**作为 P1 完成后仍不锁时的下一分支**，现在不动。
- 局端 NAS-Port-Id `XG`/`GP` 与 RADIUS 校验不匹配：属 OLT/BRAS 侧字段，光猫不可控，已排除。

### 4.2 当前判断

- 改造面收敛在 patch 608 的 GPON RX 分支（P1+P2）与两处取证增强（P3+P4）+ 一处清理（P5）。
- 断点唯一且明确：GPON 从未校准。后面 6 段"没跑到"不等于"没问题"，因此每次真机验证都以"能否沿基线表逐段推进"为判据，而不是只看是否拨号成功。

### 4.3 下一步（建议顺序）

1. 先做 P4+P3 的取证改造，与 P1+P2 的校准改造放同一次改动：一次编译即可同时得到"校准是否生效"和"同步状态读的是哪个窗口"两类结论。
2. 逐 hunk 校验 patch 行数 → 提交到工作目录分支留痕 → 输出容器内编译命令（编译与刷机由人工执行）。
3. 真机取一份 GPON bundle，回填第三节台账，并按第一节基线表逐段比对；P1 若生效但 `hunt` 仍在，转 P3 判读；若 `lock=1` 都拿不到，才启动"前端 A2 的 `TIA_BW/PGA_GAIN` 是否适配 2.488G"这一分支。

### 4.4 回退方案

- P1/P2 只改 patch 608 的 GPON 分支与新增档表，XGS/10G-EPON 路径不受影响；若验证失败，可单文件回退到 d528c3b 的 608 patch，已跑通的 XG-PON/XGS-PON 业务不降级。
